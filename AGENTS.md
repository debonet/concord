# AGENTS.md — Concord (for every coding agent, in every project that uses it)

This file is the shared instruction set for any coding agent (Claude Code, Codex, Gemini CLI, Cursor, Aider or another) working in a project that adopts Concord. It ships in `@debonet/concord`; resolve references to `specs/`, `roles/` and `orchestration.md` from the directory containing this file. A project's own `AGENTS.md` adds that project's facts and working rules. Tool-specific files point here too and add only what is particular to their tool.

## What Concord is

This project uses IDD. Before other work, read the installed package's instructions at the path printed by `node -p "require.resolve('@debonet/idd/INSTRUCTIONS.md')"`. If IDD is not installed, run `npm install @debonet/idd` first.

Concord keeps a project's specs and tests in step. Its specs are the authority on everything below; read the one a question turns on:

* `specs/concord-process.md` — the process, what a project declares, what stops a commit
* `specs/spec-map.md` and `specs/spec-map-line-types.md` — markers, line types, links, the checker's lists and queries
* `specs/spec-map-interactive.md` — hand checks
* `specs/link-refinement.md` — reviewing file-wide code links for narrower regions
* `specs/spec-coverage.md` — coverage
* `specs/spec-conflicts.md` — ranked lexical candidates for specification conflicts
* `roles/conflict-reviewer.md` — read-only review of one conflict candidate per agent invocation
* `roles/link-refiner.md` — reviews one hashed shard of file-wide code links through completion
* `specs/concord-hook.md` — installing the commit gate
* `specs/agents-sync.md` — generating agent-tool files from the roles
* `specs/observations.md` — the observations file, observation ids, citations and retirement
* `docs/` — one migration note per Concord change that adopting projects must follow; each guide's filename and heading state its effective date
* `docs/migration-20261123.md` — required migration reading for projects adopted before the region-link and diff-sidecar model
* `docs/migration-20261125.md` — move human intent and guidance markers into files under `intent_directories` and `guidance_directories`
* `docs/migration-20261126.md` — replace legacy path-only `@tested-by` links with specific test-unit links

## The rules every agent follows

1. **Specs before code.** A change in behaviour is first written into the spec that owns it, then implemented. Two roles do this: the **architect** owns specs and never edits code (`roles/architect.md`); the **fixer** owns code and tests and never edits specs (`roles/fixer.md`). A **conflict-reviewer** gets one candidate with `concord spec-conflicts --nextreview`, examines it, and returns evidence and a verdict; it does not edit files or the shared conflict ledger (`roles/conflict-reviewer.md`). The **link-refiner** gets one candidate shard, refines its candidates through completion, and reports its result (`roles/link-refiner.md`). The calling agent coordinates parallel shards and records conflict verdicts. A tool with subagents runs these roles as separate agents; a tool without plays architect first, then fixer, and does not let the fixer step change a spec.
2. **Statements are marked.** Every provable sentence in a spec carries `{#s-xxxxxx}` with its roots (`<m-…` for the human's recorded words, `<arch` for a decision made on the human's behalf). New markers are written as placeholders (`{#s-?}`) and given ids by the assign command; never invent an id.
3. **Links identify their source regions.** `@proves` directives form indentation-scoped test groups. Code directives `@implements`, `@tested-by`, and `@checks` use the same group rules: an initial contiguous group at the top of a code file applies file-wide; a blank line or intervening comment ends that header group, and later groups own source regions. Deeper groups add links to enclosing groups; a same-or-less-indented group replaces that level and closes deeper groups. Test-framework nesting does not extend a group's scope. Use the statement hash printed by the checker. Test names carry nothing: there are no named test cases.
4. **The checker runs from the project root**: `concord spec-map` and `concord spec-coverage`, through the project's `spec-map` / `spec-coverage` targets. In Concord's source checkout, use its local `bin/concord` executable for checker and utility commands; never fall back to an older global install. The project root holds `concord.json`. Never write a checker of your own; a checker defect is a change to Concord.
5. **After every spec change:** run `concord spec-map --assign`, then `concord spec-map`. Stale links, link lines that do not resolve, dangling targets, re-derive, unstamped, underived and malformed must all be 0.
6. **The human's words are recorded verbatim** as motive (`m`) lines before anything is derived from them, and a decision the human did not make is rooted `<arch` so the checker lists it for the human to ratify or overrule.
7. **Commits are gated.** A project's pre-commit hook runs `concord spec-map --gate`; a commit it refuses is fixed, never bypassed.
8. **Observations go in the observations file, never in a rules file.** A mistake, a correction or an unexplained red is recorded as an entry with an id in the project's observations file, stated as what was observed, with no date or story unless germane. A standing rule holds only itself, its check and the ids of the observations it rests on. An observation is retired, its entry and every citation deleted, only when the checker lists it retirable (`specs/observations.md`).
9. **Run the full test suite before every fixer completion.** After the fixer's final code or test change, run the project's full declared test-suite command, fix any failures, and report completion only after it passes. This is mandatory even when no one explicitly asks for tests; targeted runs do not replace the final full-suite run.
10. **Use the conflict reviewer for every candidate.** When asked to review potential specification conflicts, first run `concord spec-conflicts`. While `concord spec-conflicts --count` is greater than zero, launch as many generated `conflict-reviewer` agents concurrently as the harness allows. Each reviewer runs `concord spec-conflicts --nextreview` at startup; it atomically timestamps and returns one eligible candidate plus `remaining_count`. Reviewers return that count; when it is positive, launch another reviewer if capacity is available. An extra reviewer may get no candidate and report that none are available now. Wait for active reviewers, record completed verdicts with `concord spec-conflicts --mark`, and repeat. The default cooldown is one hour; `--since <duration>` changes it. Failed or unanswered reviews become eligible again when their handout timestamp passes the cooldown. Do not infer verdicts from score or status. **Never inspect or modify `spec-conflicts.json` manually.** Use Concord commands for every read or update; the calling agent alone records verdicts.
11. **Migrate older links:** before changing existing `@implements`, `@tested-by`, `@checks`, `@proves` or `.concord` annotations in a project adopted before November 23, 2026, read `docs/migration-20261123.md`.
12. **Refine file-wide links deliberately.** During a migration that offers link refinement, explain the scope and ask the user whether to run it; follow the applicable migration guide's yes/no steps. Outside a migration, use the generated `link-refiner` agent when the harness can launch agents. Choose a fanout and launch one agent for each unique `index/fanout` shard. Each agent reads the supplied spec or check, implementation and tests; narrows a valid link when evidence supports a region; keeps it file-wide only when it validly applies across the file; removes it when the relationship is false or unrelated; and runs `concord spec-map` after the last globally open candidate in each source file, as directed by `next_command`. Candidates are hashed independently, so one source file may be edited by different shards. Immediately before editing, reread the file and verify the directive is still at the reported location; if it shifted or changed, fetch a fresh candidate id. Make minimal patches against current contents. To rebalance, tell every active agent to finish its current candidate and stop before calling `--next`; wait for all to confirm they are paused; count each old shard with `concord link-refine --count --shard <index>/<old-fanout>`; then select the new fanout, stop the old assignments, and restart one agent per new shard. Completed decisions persist, and stable review ids redistribute open candidates under the new fanout. If agents cannot be launched, review one shard at a time with `concord link-refine --next --shard <index>/<fanout>`. Never edit `.concord/link-refinements.json` or `.concord/link-refinements/` manually. After integrating all shards, run a final `concord spec-map`.
13. **Apply migrations when adopting or updating Concord.** Read `Concord migrations applied through: YYYY-MM-DD` in the project's root `AGENTS.md`. Use the dated migration index in the Concord README and apply every newer guide that applies to the project, in date order. If the record is absent, review all guides from the beginning. After all applicable migrations and their required checks are complete, add or update the line to today's date; it records that migrations through that date have been reviewed and applied or found inapplicable.
14. **Show the Concord tree when asked.** From the project root, run `concord tree --output tmp/concord-tree.html`, then open that file in a browser and show the result.

## Adopting Concord in a project

For a project-local package install, use `npm install --save-dev @debonet/concord --cache ./tmp/npm-cache`; Concord is development tooling.

When the human asks to adopt Concord, the harness checks whether `concord` is installed, installs `@debonet/concord` globally with `npm install --global @debonet/concord` if needed, then runs `concord init` from the project root inside the harness. Init creates missing baseline settings and build commands, writes the adoption line, and attempts hook installation. Review its changes and resolve any reported conflicts or gate failures before launching an architect or fixer. That request is the adoption decision even if the project currently has an opt-out line; init replaces a standalone former opt-out or legacy adoption line. For projects where adoption has not been requested, do not run setup or add Concord files unless the adoption rule in `specs/concord-process.md` calls for resolving an undecided project with the human. A project uses Concord when its root `AGENTS.md` holds the standalone adoption line. A project that does not use it holds `This project does not use Concord.` instead. `concord migrate` remains available to update only a former marker. In a project that holds neither current line, the session asks the human which before any architect or fixer is launched there, and writes his choice into its `AGENTS.md`; nothing of Concord's is added to a project that has not opted in (`specs/concord-process.md`, Which projects use Concord). A project that has opted in is fully adopted when its build spec declares `spec-map` and `spec-coverage` targets that call `concord spec-map` and `concord spec-coverage`, its root holds a `concord.json` (`specs/concord-process.md`, What a project declares), its root `AGENTS.md` holds that project's facts and working rules after the Concord line, and its committed pre-commit hook runs the gate (`concord concord-hook install`, run once per clone). A project that carries its own checker retires it.

## Publishing the Concord npm package

For npm commands in the Concord source project that need registry credentials, set `NPM_CONFIG_USERCONFIG="$HOME/.npmrc-concord"` for that command. The token belongs in the private user-level `~/.npmrc-concord` file (mode `600`), not the shared `~/.npmrc`, a repository `.npmrc`, or any tracked file. Other projects should use their own user-level npm config file. For example:

```sh
NPM_CONFIG_USERCONFIG="$HOME/.npmrc-concord" npm publish --access public
```

Claude Code's agent files (`~/.claude/agents/<role>.md`) and Codex's custom agents (`$CODEX_HOME/agents/<role>.toml`, or `~/.codex/agents/<role>.toml`) are generated from the installed package's `roles/` by `concord agents-sync`. In the Concord source project, change a role in `roles/<role>.md` or its tool metadata file, then run `npm run agents-sync`; never edit a generated agent file.

Each agent tool's own instruction file tells its agent to run `concord agents-sync`, with no argument, at the start of each session, before any other work. A run with nothing changed does no work and needs no write access (`specs/agents-sync.md`, When nothing changed).
